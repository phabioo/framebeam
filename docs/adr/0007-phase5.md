# ADR 0007: Phase 5, users, firmware, settings pages, gamepads, installer

- Status: accepted
- Date: 2026-10-06
- Decided by: Fabio (accepted 2026-10-06)

## Context

Phase 5 (`docs/workflow.md` phase plan, `docs/architecture/07-poc-scope.md`) adds: Hub users with onboarding invites and an upload permission, the systems and cores registry, the firmware path, the Player pages Emulation and Controllers, SDL3 gamepads, dark/light appearance, the remaining Hub pages (3l, 3n, 3o phase-5 parts) and a Windows installer. The systemd unit already exists (`packaging/linux`). Relevant architecture: `05-emulation.md` (cores, BIOS/firmware, settings hierarchy), `06-controllers.md`, `10-identity-pairing-tls.md`. OpenAPI goes from 1.2.0 to 1.3.0; `protocol_version` stays 1, new handshake features are additive.

## Decisions

### D1 Users and onboarding invites (Hub page 3n)

- An admin creates an invite on the Hub page Users. Code format `FB-XXXX-XXXX` (Crockford base32 without 0/O/1/I/L), single use, expiry 15 min / 1 h (default) / 24 h, toggle "Authorize first device directly" (default on). Only a hash of the code is stored. The admin can revoke an active invite; history shows redeemed, expired and revoked. Invites are not Session invites.
- The Player redeems with `POST /api/v1/invites/redeem` (no auth, rate limited like pairing), body `{code, display_name, device_id, device_name, platform, arch, player_version, protocol_version}`. This creates a Hub-local user (role `user`, no password; username is a unique slug of the display name).
  - Toggle on: 200 `{status: approved, hub_id, user_id, device_credential}`; the device is trusted immediately.
  - Toggle off: 202 like `createPairingRequest` (`request_id`, `poll_token`, `status: pending`, `expires_in`). The pending request is pre-assigned to the new user; the admin allows or denies as usual; polling uses the existing endpoint.
  - Errors: invalid, expired, used and revoked codes all return 404 `invite_invalid` (no enumeration); taken display name 409 `display_name_taken`; 429 rate limited.
- Display names are unique per Hub (case-insensitive), 1-32 characters, trimmed.
- Admin can disable and enable users (not the admin itself). A disabled user gets 401 `user_disabled` on token exchange and every authenticated call; their WSS connections are closed and their Sessions end (reuse an existing `session_ended` reason if one fits, else add one; open; settled in the implementation notes: `owner_disconnected`). Saves and uploads are preserved.
- Clients page: a pending request has an "Assign user" select (default: the pre-assigned invite user, else the admin); the approved device belongs to the selected user.
- No user deletion and no role change in phase 5.

### D2 Upload permission

- Hub setting `allow_user_uploads` (default off), toggle in the Settings card "Library".
- New `POST /api/v1/games` (Bearer): raw body (`application/octet-stream`), filename and optional title via query or header. The admin is always allowed, users only when the setting is on (403 `uploads_disabled`). Validation and dedup are the same as the web upload (409 duplicate with the existing game id). `uploaded_by` is the caller.
- Handshake feature `uploads_v1` is announced only when the caller may upload, so the Player shows the button only then.
- Managing or deleting other users' entries stays admin-only, in the web interface.

### D3 Systems and cores registry (Hub page 3l)

- The Hub registry is seeded for `nds`: preferred core `melonds_ds`, expected version `1.4.0` (verified: the release build of the pinned tag v1.4.0 reports `library_version` "1.4.0"), platforms `windows-x86_64` (plus `linux-x86_64` for development), provisioning "Included in the Player". The admin can edit the expected version (empty = any).
- The handshake already carries `cores`. The Hub compares with the registry: missing core gives problem `core_missing`, another version `core_version_mismatch`. Both are reported but `compatible` stays true (warning, launch allowed). A protocol mismatch still sets `compatible=false`.
- The Hub stores the last handshake report per device (platform, arch, player version, cores, time) and shows it under "Reported by clients" with status compatible / version mismatch / core missing / player too old.
- Core package cache: only the "LATER" placeholder.

### D4 Firmware path

- Per system a firmware mode: `builtin` (default for `nds`; melonDS DS uses its built-in FreeBIOS, files optional) or `native` (files required; the Player sets the core option `melonds_sysfile_mode` to `native`; values are `builtin` | `native`). The admin switches it on 3l.
- `nds` files: `bios7` "ARM7 BIOS" (16384 bytes), `bios9` "ARM9 BIOS" (4096 bytes), `firmware` "DS Firmware" (131072, 262144 or 524288 bytes). Target file names in the core's system dir (verified against melonDS DS v1.4.0): `bios7.bin`, `bios9.bin`; the firmware image is materialized as `firmware.bin` and the core option `melonds_firmware_nds_path` is set to that name in mode `native`. The core looks files up in the system dir or its "melonDS DS" subdir (confirmed, see implementation notes).
- Validation on upload: size must match; if the admin pinned an expected SHA-256 for that file, it must match too. No expected hashes are shipped; we neither invent nor distribute BIOS hashes. Stored as `<data dir>/firmware/<system>/<file_id>`, sha256 in the DB. The admin can replace and remove files.
- Status per file: valid / hash mismatch (only when pinned and differing) / missing / optional-missing. The nav badge "N firmware" counts required files (mode `native`) that are missing or mismatching.
- In mode `native` the core silently falls back to its built-in BIOS when a file is missing, so the Player enforces the check itself (below) and must not rely on the core to fail.
- Player API: `GET /api/v1/systems` (Bearer) returns the registry with firmware mode and per file `{id, display_name, required, present, size, sha256}`; `GET /api/v1/systems/{system_id}/firmware/{file_id}` returns the bytes (any trusted device; never logged). Handshake feature `firmware_v1`.
- The Player caches firmware in `<data>/system/firmware/<system>/<sha256>` (separate from ROMs and cores), validates size and sha256 and materializes the core's expected file names in the libretro system dir before launch. In mode `native`, if a required file is unavailable or fails validation, the library detail and the Emulation page show "Firmware required/missing" and launch is blocked. In mode `builtin` nothing is downloaded.
- No real BIOS or firmware in the repo or in tests; tests use dummy bytes of the right size.

### D5 Player Emulation page (3e) and settings hierarchy

- Local only, `<data>/settings/emulation.json`, partial overrides: `{global: {...}, systems: {"nds": {"core": "melonds_ds", "options": {...}}}, games: {<game_id>: {...}}}`. Effective value: game > system/core > global > manifest default > core default. Removing a key restores inheritance.
- Core options come dynamically from the core (`RETRO_ENVIRONMENT_SET_CORE_OPTIONS_V2`/`_V1`/legacy), captured when the core loads; the page lists only reported options (enum as select). Manifest options FrameBeam must control (software render mode, layout, OSD off) stay locked and are not shown as editable.
- FrameBeam group: "Fullscreen on start", "Default multiview" (PiP / side-by-side). A "Restart required" badge marks options that only apply at the next launch.
- Level switch Global | System/Core | Game Override; Game Override is disabled ("later").

### D6 Controllers page (3f) and SDL3 gamepads

- SDL3 (>= 3.2) is used only for gamepads (`SDL_INIT_GAMEPAD`). Audio stays on Qt Multimedia (see Deviations).
- Local profiles in `<data>/settings/controllers.json`: built-in "Standard Gamepad" and "Keyboard · Standard" (the current key map), user profiles (duplicate, rename, delete), remap via "Press a button…", reset to default, per-device profile assignment, player slot P1 (DS has one player). Mouse is DS touch (fixed).
- Mapping chain: physical input, profile, FrameBeam input, system profile `nds`, libretro joypad.
- An input test panel shows the live state of FrameBeam inputs.
- Tests use SDL virtual joysticks (no hardware in the cloud).

### D7 Dark/light

- Player: Settings page (sidebar "Settings") with Appearance Dark (default) | Light | System, stored in the Player settings. `Theme.qml` already has both palettes (light derived from the Hub tokens). The game view stays dark.
- Hub: Settings "Appearance" Light (default) | Dark | System, stored as Hub setting, applies to the web interface (dark palette derived from the Player tokens; System via `prefers-color-scheme`).

### D8 Windows installer

- Inno Setup 6 script `packaging/windows/framebeam-player.iss`, built in Windows CI from the existing package.
- Per-user install by default (no admin rights) to `%LOCALAPPDATA%\Programs\FrameBeam Player`, so the portable `<exe-dir>/data` stays writable ([ADR 0004](0004-player-portable-data.md)). This is what `{autopf}` resolves to for a non-admin install. An admin install is possible; then `<exe-dir>/data` is not writable and data falls back to AppData per ADR 0004. Start menu shortcut, optional desktop shortcut. The uninstaller keeps `data\` unless the user ticks "Also remove my data". Licence texts are included (GPL-3.0 core, LGPL Qt etc.).
- Unsigned (signing is outside the PoC). CI artifact `framebeam-player-windows-x64-setup`.

## Consequences

- OpenAPI 1.3.0 with new endpoints (`/invites/redeem`, `POST /games`, `/systems`, firmware download) and handshake features `uploads_v1` and `firmware_v1`; older Players keep working.
- New Hub tables for invites, user state, registry, firmware files and the last handshake report (migration in the implementation).
- New Player prerequisite SDL3 (>= 3.2) on Linux and Windows builds.
- Firmware is user-supplied; the Hub stores and serves it but ships none and pins no hashes.
- Settings are local to the Player and never synced to the Hub.

## Deviations

- Audio stays on Qt Multimedia, not SDL3 as [ADR 0003](0003-player-phase2.md) planned; SDL3 is used for gamepads only. Reason: audio already works on Qt Multimedia and nothing in phase 5 needs SDL audio.
- A core version mismatch is a warning and does not block launch (`compatible` stays true), whereas `docs/architecture/05-emulation.md` requires a matching version. Accepted by Fabio with this ADR.

## Implementation notes

Details of behavior: [hub-internals.md](../reference/hub-internals.md), [player-internals.md](../reference/player-internals.md) (moved there from the Hub and Player READMEs on 2026-10-08).

Hub

- Invite code alphabet `23456789ABCDEFGHJKMNPQRSTUVWXYZ` (31 symbols, about 40 bits). The code is shown only once at creation; no fragment is stored and there is no "Copy link".
- Redeem with a `device_id` of an already trusted device returns 409 conflict.
- Redeem rate limit: 5 per IP per minute plus 30 failed attempts per minute globally.
- Disabled users: their Sessions end with `owner_disconnected`, WSS closes with reason `user_disabled`; token exchange answers `user_disabled` only after a valid credential (no account probing). This settles the open `session_ended` reason in D1.
- Display names are unique via a DB index.
- Systems and firmware definitions live in the Hub DB (migration 0004).
- A firmware upload whose hash differs from a pinned hash is rejected; "Hash mismatch" appears only when a pin changes after upload. Players see a mismatching file as not present (`/systems` present=false, download 404), so native mode blocks the launch. Replacing a file keeps a backup until the metadata update commits.
- Firmware download is served on the mux with ETag.
- `uploads_v1` is announced per caller.

Player

- BIOS lookup by melonDS DS: `system/"melonDS DS"/`, then `system/`. FrameBeam materializes `bios7.bin`, `bios9.bin`, `firmware.bin` into `<data>/system` and sets `melonds_sysfile_mode` / `melonds_firmware_nds_path`.
- If `/systems` fails, the Player allows a builtin launch with "Status unavailable".
- melonDS DS registers options only in `retro_load_game`; the Player probes it in no-game mode at startup and caches the result in `<data>/cache/core-options/`.
- `locked_core_options` in the manifest (render mode, layouts, gap, touch mode, OSD) are hidden and never overridden.
- Launch order: manifest defaults, then game > system > global overrides, then firmware options, then locked values.
- Controllers: four D-pad rows, no LID row (the `nds` profile has no lid input); built-in profiles are read-only (duplicate to edit); gamepads are polled every 8 ms; the first pad is P1.

Packaging and build

- Installer: per-user into `{autopf}`; an admin install is possible, then data falls back to AppData per [ADR 0004](0004-player-portable-data.md). The uninstaller asks before removing data; a silent uninstall keeps it.
- SDL3 3.2.30: source build on Linux (`SDL_UNIX_CONSOLE_BUILD`), vcpkg on Windows.
