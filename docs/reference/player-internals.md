# Player internals

How the FrameBeam Player (`client/`, C++20/Qt 6/QML) is built and what it does in detail. Using it: [player.md](../guides/player.md). Build and test: [development.md](../development.md). Rules for agents: `client/CLAUDE.md`. Decisions: [ADR 0003](../adr/0003-player-phase2.md), [ADR 0004](../adr/0004-player-portable-data.md), [ADR 0005](../adr/0005-saves-phase3.md), [ADR 0006](../adr/0006-sessions-phase4.md), [ADR 0007](../adr/0007-phase5.md), [ADR 0009](../adr/0009-finish-poc.md), [ADR 0013](../adr/0013-opengl-hardware-rendering.md), [ADR 0014](../adr/0014-player-ui-pass.md).

## Structure

- `core/`: profiles, ROM cache, credential store, version, local settings stores (`player.json`, `emulation.json`, `controllers.json`) (`framebeam_core`)
- `network/`: Hub connection (HTTP/TLS with fingerprint pinning), library, ROM download, WSS client (`hubsocket`), save API and sync (`saveapi`, `savesync`), Session API, firmware provisioning, game upload, systems registry; CLI `framebeam_player_cli` in `network/cli/`
- `emulation/`: `EmulatorBackend`/`LibretroBackend`, system manifest and core profiles (`manifests/systems/<system>.json`, `manifests/cores/<core_id>.json`), core locator, `core_options`, `firmware_materializer`, `emulation_runner`, test-ROM generator in `emulation/tools/`
- `input/`: `framebeam_input`: SDL3 gamepad service (hotplug, state, capture) and the mapping chain; `framebeam_sdl3` (SDL3 target)
- `ui/`: QML module `FrameBeam.Player` as static lib `framebeam_ui`; screens: connection, pairing, library, game/Session/multiview, Emulation, Controllers, Settings
- `app/`: executable `framebeam_player`
- `launcher/`: Windows only, target `framebeam_player_launcher` (output `<build>/launcher/framebeam_player.exe`): tiny launcher without Qt (static CRT) that starts `bin\framebeam_player.exe` with the same arguments
- `media/`: `framebeam_media`: H.264 encoder/decoder (libavcodec), Opus, audio resampler, `SessionHost`/`SessionViewer` (WebRTC via libdatachannel), plus `framebeam_media_deps` smoke test
- `testutil/`: test helpers

## Dependencies

- OpenSSL (`OpenSSL::Crypto`, Ed25519 verification of the update index): Linux apt `libssl-dev`, Windows vcpkg `openssl` (already built transitively by libdatachannel).
- Qt >= 6.4 (Core, Network, Gui, Quick, QuickControls2, Multimedia, WebSockets, Test); not via vcpkg. Linux: apt, Windows: install-qt-action (see `.github/workflows/ci.yml`).
- CMake >= 3.25, Ninja; vcpkg (`scripts/bootstrap-vcpkg.sh`) for further packages.
- Media ([ADR 0006](../adr/0006-sessions-phase4.md)): Linux apt `libavcodec-dev libswscale-dev libopus-dev qt6-websockets-dev libssl-dev` plus libdatachannel from `scripts/fetch-libdatachannel.sh` (pinned, `scripts/libdatachannel.pin`); Windows vcpkg (`client/vcpkg.json`, platform windows; FFmpeg with `nvcodec`, `qsv`, `amf` since 0.1.1, [ADR 0009](../adr/0009-finish-poc.md)).
- SDL3 >= 3.2, gamepad/joystick subsystem only (audio stays on Qt Multimedia; CMake target `framebeam_sdl3` in `input/`). Linux: pinned source build via `scripts/fetch-sdl3.sh` (`scripts/sdl3.pin`, no video/audio, no extra apt packages; Ubuntu 24.04 has no SDL3 package), found through `SDL3_ROOT`; Windows: vcpkg port `sdl3` without features (`client/vcpkg.json`). The `input_sdl3` test proves it links and runs headless with a virtual joystick.
- melonDS DS core (pinned, `scripts/melonds-ds.pin`): `scripts/fetch-melonds-ds.sh` (Linux) or `.ps1` (Windows). DeSmuME (unpinned buildbot nightly): `scripts/fetch-buildbot-core.sh desmume` / `make fetch-desmume`; test path `FRAMEBEAM_DESMUME_CORE`. No core in the repository.
- Windows release builds use the `x64-windows-release` overlay triplet (x64, dynamic CRT and libraries, Release-only dependency builds); the debug preset continues to use the standard `x64-windows` triplet.

## Data storage

Summary for users: [player.md](../guides/player.md#data-directory).

Portable by default: `<directory of the executable>/data` (ROM cache, `profiles.json`, `device.json`, `hubs/<id>/` incl. saves, `system/`, `probe/`), provided a real write test succeeds there. Otherwise it falls back to AppData (`QStandardPaths::AppDataLocation`) with a log note (`framebeam.profiles`). If the portable folder has no `profiles.json` yet, existing AppData content is copied once (the source remains unchanged, nothing is overwritten, `device_id` is preserved, the ROM cache is re-downloaded). Credentials stay in the OS credential store. `--data-dir` and `FRAMEBEAM_DATA_DIR` take precedence.

## Users, uploads, firmware, appearance ([ADR 0007](../adr/0007-phase5.md))

- **Invite codes:** on the pairing step choose "I have an invite code", enter code and display name. 200: paired immediately (credential stored like a normal pairing); 202: the usual "Waiting for admin approval". Errors (`invite_invalid`, `display_name_taken`, rate limit) are shown in place. CLI: `framebeam_player_cli redeem-invite <address> --code FB-XXXX-XXXX --name <name> [--accept-fingerprint]`. A user disabled on the Hub (`user_disabled`) gets "This user is disabled on the Hub" on the connection screen; the credential is kept, there is no retry loop (Retry is a manual action).
- **ROM upload:** "Upload ROM" in the Library header, only if the handshake has `uploads_v1`. The file is streamed (not read into memory) with progress; "Already in the library" selects the existing game (409). The file dialog is `QtQuick.Dialogs`; if that QML module is missing (Linux: apt `qml6-module-qtquick-dialogs`), a path field is shown instead. CLI: `game upload <file> [--title T]`.
- **Firmware:** with `firmware_v1` the Player reads `/systems`. Mode `builtin` (default): nothing is downloaded, core option `melonds_sysfile_mode=builtin`. Mode `native`: required files are downloaded to `<data>/system/firmware/<system>/<sha256>` (size and SHA-256 checked, separate from ROMs), copied as `bios7.bin`, `bios9.bin`, `firmware.bin` into `<data>/system/` (melonDS DS looks there; file names and core options come from `emulation/manifests/systems/nds.json` and the core profile) and the core gets `melonds_sysfile_mode=native` plus `melonds_firmware_nds_path=firmware.bin`. A required file that is missing on the Hub or fails validation shows "Firmware required/missing" with the file names in the detail pane and blocks the launch ("Check firmware again" re-reads the registry). Without `firmware_v1` the Player behaves as builtin. Only file ids and hashes are logged. CLI: `systems` prints mode and file status.
- **Core warnings:** handshake problems `core_missing` / `core_version_mismatch` appear as a non-blocking banner in the Library. The handshake reports the chosen core with the version from `retro_get_system_info`. Since 0.8 (ADR 0017 D1 / ADR 0020 D3) a major-version block applies only where both sides report a semver version; build ids `YYYY.MM.DD[.N]` only warn.
- **Settings:** sidebar "Settings" > Appearance Dark (default) | Light | System, stored in `<data>/settings/player.json`. System follows the OS color scheme (`Qt.styleHints.colorScheme`, Qt >= 6.5; on Qt 6.4 it falls back to dark). The game view always stays dark.
- **Emulation page** (sidebar "Emulation", design 3e): system cards (core name + version, "Ready · included in the Player", firmware "Built-in BIOS" / "Firmware from Hub · verified" / "Firmware required/missing"), level switch Global | System / Core (Game Override is disabled, "later"), group "FrameBeam" (Fullscreen on start: the window goes fullscreen while a game is shown; Default multiview: PiP or side-by-side, applied when a game starts) and a group with the options **the core reports** (libretro core options V2/V1/variables incl. categories, values, defaults; shown as selects, nothing invented). The core is loaded once without a game to read them (not possible while a game runs: only one core per process) and the result is cached in `<data>/cache/core-options/<core_id>.json`. Settings are local, stored as explicit overrides only in `<data>/settings/emulation.json` (`global`, `systems.<id>.options`, `games.<id>`); effective value = game > system/core > global > manifest default > core default; "reset" removes the key. Values apply at the next launch (a game that is running shows "Restart required"). FrameBeam keeps control of `melonds_sysfile_mode`, `melonds_firmware_nds_path` (firmware path from the Hub) and the options marked in `locked_core_options` of the manifest (screen layout, on-screen display, touch mode; the render mode is not locked since 0.5, so the Emulation page offers Software/OpenGL, ADR 0013): they are not shown and user overrides for them never reach the core.
- **Controllers page and gamepads** (sidebar "Controllers", design 3f): SDL3 gamepads (`SDL_INIT_GAMEPAD` only, no SDL video; events pumped by a Qt timer) with hotplug; the first connected gamepad is P1 and drives the game together with the keyboard (merged joypad mask). Gamepads are off if SDL does not initialise (handshake `input.gamepad` reports this); keyboard and mouse always work. Chain: physical binding -> local profile -> FrameBeam input -> system profile `nds` -> libretro joypad. Built-in, read-only profiles "Standard Gamepad" (NDS A = east button) and "Keyboard · Standard" (map below); own profiles can be duplicated, renamed, deleted, reset and remapped with "Press a button…" (gamepad buttons, D-pad, left stick as D-pad, triggers as buttons; keyboard keys, Esc cancels). A device gets its profile assigned (gamepads by SDL GUID). Mouse = DS touch (fixed). The input test shows the live FrameBeam inputs of the selected device. A LID row appears only for input profiles that have a lid input (none yet). Profiles are stored in `<data>/settings/controllers.json` and stay local; they are never synchronized.

## Runtime details (0.7.x)

- **Controller split:** `PlayerController` delegates to `CoreCatalog`, `GameDetail`, `HubPresenter` and `GameStarter` (`ui/`, [ADR 0017](../adr/0017-player-tech-debt.md) D3). Session visibility lives in `settings/player.json`; a core whose major version differs from the Hub's expected one blocks the launch (D1).
- **Speed-up:** libretro fast-forward with a selectable speed (1.5x to 8x); the screen frame rate stays at the base rate and hardware frames are scaled down on the GPU before the readback ([ADR 0018](../adr/0018-player-speed-up.md), [ADR 0013](../adr/0013-opengl-hardware-rendering.md)). Readback uses PBOs; `FRAMEBEAM_SYNC_READBACK=1` forces the synchronous path.
- **Hotkeys:** stored in `settings/controllers.json` (`hotkeys`, non-default entries only); a hotkey wins over the keyboard profile and never reaches the core.
- **GPU-direct encoding:** `GpuEncodeBridge` and `media/cudaglcapture` hand the core's OpenGL texture to a second `h264_nvenc` encoder; failures fall back to readback frames ([ADR 0019](../adr/0019-gpu-direct-nvenc.md)).
- **Background game:** leaving the game view pauses the running game and keeps it loaded; quitting is explicit.
- **Live saves:** "Manage saves" in the game panel (`SaveHistoryController`); restore and upload stop the game, write the save and start it again, so the core is never unloaded and reloaded inside one run.
- **Audio:** `AudioOutput` starts the Qt sink in pull mode and reads from `AudioQueueDevice`, which pads with silence only when completely dry (Qt 6.8 WASAPI push mode went idle and stayed silent); underruns are counted once per dry spell.
- **Core choice (0.8, [ADR 0020](../adr/0020-cores-from-the-libretro-buildbot.md) D6):** the manifest is split into a system manifest (display, input, labels, extensions, firmware files) and core profiles (library basename, option defaults and locks, firmware option mapping, legacy aliases such as `melonds_ds`). A core without a profile resolves to an experimental manifest. `network/corechoice.*` picks the core: game setting > system setting > the Hub's `default_core_id` (> legacy preferred core of a Hub without `cores_v2`), restricted to the cores the Hub serves; a stored choice the Hub no longer serves is ignored and reported. `ui/corecatalog.*` feeds the "Core" select on the Emulation page. The signed core index check is gone; size and SHA-256 against the Hub stay. The update check still uses `FRAMEBEAM_PLAYER_TRUST_KEYS` (`core/updatesig.*`).
- **Save snapshot before a core change (ADR 0020 D7, `network/savesync.cpp`):** `sync.json` records `writer_core_id` / `writer_core_version`. A start with another core or build first copies the local save to a `core-change` backup, then creates a manual snapshot on the Hub (`Before core change: <old> <ver> -> <new> <ver>`, cut to the Hub's 64-byte label limit) and records the new core. A failed snapshot or an unreachable Hub with a local save blocks the start; a Hub without snapshots (no `saves_v2`) gets the local backup only. First start (nothing recorded) just records.
- **Save file per core profile (ADR 0020 D7, `core/dsvsave.cpp`, `network/savesync.cpp`):** the core profile's `save` block names the source (`save_ram` = Player persists SAVE_RAM as `<rom>.sav`; `core_file` = the core writes its own file, `.dsv` with format `desmume_dsv`); `short_dir: true` (Azahar) hands the core `<baseDir>/c/<16 hex of sha256(hub/user/game/slot)>` instead of the save directory (Windows MAX_PATH; `SaveStore::shortCoreDir`, the profile's `short_dir_subfolder` (`Azahar`) is moved over once from the old dir); cores without profile are `auto` (SAVE_RAM if reported, else the newest candidate file, as before). The Hub slot and the sync always use the raw `<rom>.sav`; for profiled cores exactly that file, never the newest file, and `.dsv` is never a candidate. For `desmume_dsv`: at start an unsynced `.dsv` (hash differs from `core_file_sha256` in `sync.json`) is imported into `.sav` (old `.sav` kept as `core-file` backup), after the start sync the Hub's raw save is written as `.dsv` (raw + footer as DeSmuME's `BackupDevice::ensure`: text, 6 x u32 LE size/padSize/type/addr_size/mem_size/version 0, cookie `|-DESMUME SAVE-|`), and during play and at the final sync the `.dsv` is converted back before upload. Footer validation is strict; an unparsable `.dsv` is left untouched, not uploaded, reported (`coreSaveProblem`) and blocks the next start. Layout taken from libretro/desmume `mc.cpp` (sha256 in the `dsvsave.h` comment).
- **Core cache:** a verified core file is memoised by size, mtime and change time; files written less than 2 s before the check are always re-hashed.
- **Identity:** the sidebar shows the Hub user name from the handshake `user` (stored per Hub profile) above the device name; the app icon comes from the logo spec (`scripts/gen-player-icons.py`).

## Version and automatic updates (0.3)

Spec: [ADR 0011](../adr/0011-automatic-updates.md) and `docs/roadmap.md`; user-facing description: [updates.md](../guides/updates.md).


- **Version:** the root file `VERSION` (`X.Y.Z`, shared with the Hub) feeds `project(... VERSION)`. CMake cache variables set by CI: `FRAMEBEAM_VERSION` (full SemVer, default `<VERSION>-dev`), `FRAMEBEAM_CHANNEL` (`stable` | `beta` | `dev`, default `dev`; `test` is accepted as an alias of `beta`), `FRAMEBEAM_COMMIT`. `framebeam_player --version-json` prints one line to stdout (also when redirected on Windows), e.g. `{"product":"player","version":"0.3.0-dev","channel":"dev","commit":"","protocol_version":1,"min_protocol_version":1}`.
- **Index:** `core/updateindex.*` (schema 1, validation, SemVer selection, protocol compatibility), `core/updatesig.*` (OpenSSL Ed25519; sig line `ed25519 <key_id> <base64>`; compiled-in release key plus env `FRAMEBEAM_PLAYER_TRUST_KEYS`, comma-separated base64, for tests). Index URL: env `FRAMEBEAM_PLAYER_UPDATE_INDEX_URL` or the default `updates-index` release; `file://` is accepted for tests (then also for artifact URLs).
- **Channel:** `beta` (pre-release builds from every change on main) considers beta and stable releases, `stable` only stable, compiled `dev` means off until a channel is chosen in Settings > Updates. Never a downgrade; releases that need a newer Hub (protocol) are shown, not installed.
- **Flow (`core/updater.*`):** check 10 s after start, then every 1 h (beta) / 24 h (stable); download of the `installer` artifact to `<data>/cache/updates/<version>/` (size and SHA-256 checked, together with the signed index it was chosen from). Stable: banner "FrameBeam Player X is available" with "Install and restart", installs only after the click. Beta with automatic install (default): downloaded in the background, banner "Restart to update", and a verified staged installer is applied at the next start before the main window. The staged installer is re-verified (signature, size, hash, strictly newer than the running version) before it runs. Nothing is applied during a game or a watched Session.
- **Apply:** only for an installed Windows Player (`unins000.exe` in the install root): `<setup> /SILENT /SUPPRESSMSGBOXES /NORESTART /UPDATE` plus `/ALLUSERS` (install root not writable, UAC) or `/CURRENTUSER`, then the Player quits. Otherwise (portable zip, dev build, Linux) the Settings page only shows the release and its link.
- **Install layout:** `{app}\framebeam_player.exe` (launcher) and `{app}\bin\` (Player, DLLs, Qt, qml); data stays `{app}\data` (the install root is the parent of `bin` when it contains `framebeam_player.exe`). The Player holds the named mutex `FrameBeamPlayer` (every instance holds a handle, instances are not limited; the installer waits until none does) and uses the AppUserModelID `FrameBeam.Player`.
- **Settings** (`<data>/settings/player.json`): `update_channel` (`stable` | `beta`, absent = `update_channel_default`; an old `test` is read as `beta` and rewritten on save), `update_channel_default` (`stable` | `beta`, written once on the first successful index load while no channel is selected: `stable` if the index lists the running version as stable, else `beta`; never re-resolved, [ADR 0016](../adr/0016-release-numbering-and-promotion.md)), `update_auto_install` (absent = on for beta).
- **CLI:** `framebeam_player_cli update-check [--channel beta|stable] [--index-url URL] [--current-version V] [--hub-protocol P[:MIN]]` prints the selection as JSON (`status`: `available` | `up_to_date` | `incompatible` | `disabled`, plus `release`, `artifact`, `skipped`); exit 1 with `{"status":"error",...}` on download or signature errors. Runs on Linux, needs no Hub.
