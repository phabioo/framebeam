# Features as built

What the server, the protocol and the app do today, by area. Status by version: [roadmap.md](roadmap.md). How to use them: [documentation index](README.md). Administration is done in the server web admin today; 0.18 moves it into the app and removes the web admin. The admin API (`/api/v1/admin/...`, feature `admin_v1`) already covers everything the web admin does.

**Uzume server** (`server/`)

- Admin setup from the app with a setup code (`POST /api/v1/setup`, printed at start and by `uzume-server setup-code`), via `setup-admin`, and via `/setup` in the web interface (loopback only).
- Server commands for setup and emergencies: `setup-code`, `code` (security code of the certificate), `reset-admin`, `status`, `update`, `backup`, `restore`, `reset` on Windows, Linux and in Docker ([hub-configuration.md](guides/hub-configuration.md#server-commands)).
- HTTPS with a self-signed certificate (or your own certificate); the fingerprint is logged at startup. The server renews its own certificate at startup when it is expired or expires within 30 days (`uzume-server renew-cert` does it on demand, or "Renew now" in Settings › Security without a restart; key and certificate are written atomically); the Settings page shows "Expires within 30 days". Own certificates are never modified.
- Web interface with login (admins only): Library (upload and "Rescan folder" import), Saves, Systems & Cores, Clients, Users, Settings.
- Pairing of new devices with Allow/Deny; issue and revoke tokens (Revoke); Delete removes a device entry for good (confirmation page, saves are kept).
- ROM upload in the web interface.
- ROM download via API with Range and ETag.
- Versioned saves per user and game (API tag `saves`, added in API 1.1.0, `protocol_version` stays 1, handshake feature `saves_v1`); the server stores the save as an opaque blob and never merges it.
- Web page "Saves" (admin): slots, conflicts ("Use Hub version" / "Adopt local save"), history with Download, badge in the navigation.
- Info endpoint `/.well-known/uzume` and handshake with `protocol_version`.
- Sessions: session API (visibility "Private" / "Hub users" / "Invite only", invites, viewers), WSS presence and signaling relay, revoke on visibility change; a public default STUN server (`stun:stun.cloudflare.com:3478`) when none is configured, switched off with `-ice-servers none` / `UZUME_ICE_SERVERS` or "Use no external server" in Settings › Network (0.10.x); running apps pick up ICE changes via `ice_update_v1`.
- Users and invites: Users page creates single-use invite codes (shown once, with "Copy link" to the public `/invite` page at creation), disable/enable users and delete them for good (confirmation page; removes their devices, invites, saves and save history, uploaded games stay), display names unique; Clients page assigns a pending device to a user and marks apps below the minimum protocol version as "Player too old".
- Accounts (0.18, `accounts_v1`, [ADR 0030](adr/0030-one-app-one-server-uzume.md) D5): every user can have a password (admins must); a new device signs in with user name and password instead of waiting for approval; several users on one PC; "Confirm it's you" before dangerous admin steps; own device list with sign-out; admin password reset with a temporary password; no email recovery. App side (package 7): first start, join with a security code check, `uzume://join/...` invite links, several people per PC with a switch-user sheet (Ctrl+Shift+U) and an optional 4-digit PIN for this PC, My account. The web admin is unchanged until package 12.
- Settings: "Allow users to upload games" and Appearance (Light / Dark / System).
- Systems & Cores page: installed cores per system (Update / Remove / Make default), cores available from the libretro buildbot (Install), reports from clients, firmware mode and firmware files per system (user-supplied, never shipped).
- Nintendo 3DS (0.10, [ADR 0022](adr/0022-nintendo-3ds-with-azahar.md)): system `3ds` (`.3ds .cci .cxi .3dsx .zcci .zcxi .z3dsx`; decrypted dumps only), no default core until the admin installs `azahar` from the buildbot; no firmware required or shipped. The Systems page opens on the first system with an installed default core.
- Data-driven systems (0.13, [ADR 0024](adr/0024-system-template-and-game-boy.md), [guide](guides/adding-a-system.md)): one embedded JSON per system (`nds`, `3ds`, `gb`, `gbc`, `gba`), reconciled into the database at start without touching admin state. Game Boy (`.gb`), Game Boy Color (`.gbc`) and Game Boy Advance (`.gba`) with optional boot ROM/BIOS files (`gb_bios.bin`, `gbc_bios.bin`, `gba_bios.bin`); a buildbot core is offered when its `systemid` and extensions fit (mGBA for all three, gpSP only GBA, Gambatte/SameBoy only GB/GBC); a core shared by several systems is one installed build. The server preselects no core.
- UI gaps and Multiview (0.14, [ADR 0026](adr/0026-ui-gaps-and-multiview.md), [design](design/README.md#round-3-screens-2026-10-12-014-ui-gaps-and-multiview)): server web and app Round 3 pass (dates, row action plus ⋯, amber/cyan rules, 880 px content, cards below 720 px). Server: automatic core updates per server, per system and per core (migration 0017), run admin actions (Start now/without, Pause/Resume, Finish, Archive, Delete, resend/remove invites), user rename/role/create with code, device rename, scan progress, invite expiry 1 h / 24 h / 7 days; static assets are served with content-hashed URLs (`?v=`): versioned ones are cached immutably, unversioned ones revalidate. App: update channel Off | Stable | Beta, library folder counts, plugin detail sheet ("Install both" / "Turn on both"), run detail and join dialog, Emulation without a preselected core and BIOS rows only where firmware applies, Controllers with a system selector, Uzume hotkeys with gamepad defaults (Select + button, fullscreen Select + B, speed-up Select + R2), plugin hotkeys with none, conflicts shown, Uzume keys win.
- Core package cache (0.8, [ADR 0020](adr/0020-cores-from-the-libretro-buildbot.md)): the server downloads cores from the libretro buildbot on the admin's request (installs; catalog refreshed at start, every 24 h, "Check source now"), pins the SHA-256 at install and serves them to apps; versions are `YYYY.MM.DD[.N]`; installed cores update automatically after each catalog refresh (setting "Automatic updates", default on; when off, the Update button applies). It needs HTTPS access to `buildbot.libretro.com`; offline use `uzume-server import-cores <dir>` (systemd: `install-server.sh import-cores <dir>`). Cores are not signed. Packages of the retired signed Uzume source are removed at server start (0.10); a system without a core tells the admin to install one.
- Sessions over the internet: optional embedded STUN/TURN relay (`-turn`, `-public-host`; off by default) with short-lived credentials, or Cloudflare TURN with short-lived credentials (API token as a secret on the server host, 0.10.x), or any external TURN server such as coturn on a VPS with a shared secret or static login, added in Settings → Network or via `-turn-external` (0.10.x, [coturn-on-a-vps.md](guides/coturn-on-a-vps.md)); `-public-host` accepts an external port (`hub.example.org:8443`) that invite links use; Settings shows TURN status and the router port forwards (ADR 0012).
- Save comfort: retention/thinning (`-save-keep-recent`, `-save-keep-daily`, `-save-keep-weekly`), restore from history, manual snapshots, `save_updated` push over WSS; the Saves page can restore, snapshot, delete a snapshot and create a slot (0.7.x, `saves_v3`). Save upload (`saves_v4`): upload a save file into a slot via API or web (Saves slot detail, collapsible "Upload save" form on the Saves list, "Upload save" link per Library row); the file becomes the current checkpoint and the previous one goes to history as `before_upload`.
- The signed core index endpoints of 0.4 (`cores_index_v1`) were retired in 0.8; handshake feature `cores_v2` lists the installed cores per system (`default_core_id`, `cores`).
- Server UI pass (0.7): sidebar navigation swaps only the content area; badges and tables update live (Server-Sent Events). Settings → Network edits port, embedded TURN, public host, relay range and save retention in the browser; these web settings win over `server.env`, and changes that need it are applied by a restart the server triggers itself (ports below 1024 only via `install-server.sh --port`).
- Hardening for internet exposure: TURN relay refuses internal-range peers (except connected apps) and limits allocations; the web port requires CSRF tokens on multipart forms, limits sign-in attempts, uses `__Host-` cookies with TLS and needs passwords of at least 12 characters; the app API rate limits WebSocket messages, pairing and invite redemption ([hub-configuration.md](guides/hub-configuration.md#turn-security)).
- Library: Rename and Delete per row (admin, web only; saves are kept). Saves: slot Rename/Delete (`saves_v5`; since `saves_v6` also deleting the main slot and any history version, not only manual snapshots) and save upload blocked while a Session of that game runs (0.10.x).
- Diagnostics bundle (0.10.x): Settings › Diagnostics or `uzume-server diagnostics <out.zip>` ([hub-configuration.md](guides/hub-configuration.md)).
- Operations and safety (0.17, [ADR 0029](adr/0029-operations-and-safety.md)): Docker image `ghcr.io/<owner>/uzume-server` (amd64/arm64, volume `/data`, non-root, [guide](guides/hub-docker.md)); admin page Status with CPU, RAM, disk, Sessions, TURN and recent errors, sidebar groups Play / SETUP / ADMIN, optional Prometheus `GET /metrics` with a bearer token; backup and restore (`uzume-server backup` / `restore`, schedule, retention, admin API `/api/v1/admin/backups`, [guide](guides/hub-backup.md)); problem reports from apps (`reports_v1`, ADMIN → Reports, admin API); update rollback to one of the last releases from the index with a database backup first (`uzume-server rollback`, admin API `/api/v1/admin/updates/versions|rollback|resume`).
- Ships as a Debian package and with a systemd installer script for Linux / Raspberry Pi (`packaging/linux/`).

**Protocol** (`protocol/`)

- OpenAPI 3.0.3 for `/api/v1` and WSS message schemas; OpenAPI spec version 1.29.0, `protocol_version` is 1; handshake features `saves_v1`, `sessions_v1`, `users_v1`, `uploads_v1`, `firmware_v1`, `cores_v1`, `cores_v2`, `saves_v2`, `saves_v3`, `saves_v4`, `saves_v5`, `saves_v6`, `local_setup_v1`, `reports_v1`, `accounts_v1`, `admin_v1` (admins only) and, with TURN on, `turn_v1`. See [reference/protocol.md](reference/protocol.md).

**Uzume app** (`client/`, [ADR 0003](adr/0003-player-phase2.md))

- Connection screen with server profiles and auto-connect.
- Server identification with fingerprint confirmation on first contact (TOFU); on mismatch the connection is blocked and no credential is sent. After a server certificate change the server card shows the stored and the presented fingerprint; "Trust new certificate" and then "Yes, trust this certificate" re-pin it and keep the credential (CLI: `--accept-fingerprint <sha256>`).
- Settings → Hubs: switch, remove (with confirmation), auto-connect; the current server is marked.
- Pairing via approval request, token renewal and Revoke.
- Library with search and filter.
- Hash-verified ROM cache with resumable download.
- Launch NDS games locally with melonDS DS: video, audio via Qt Multimedia, keyboard, touch via mouse.
- OpenGL hardware rendering for libretro cores (0.5): melonDS DS offers an OpenGL renderer and an internal resolution on the Emulation page (applied on next start; default Software). Hardware frames are read back to the CPU by default, so Sessions work unchanged; on Windows the game view draws them without readback (see zero-copy below). `UZUME_DISABLE_HW_RENDER=1` forces the software path; the CLI has no hardware rendering.
- Zero-copy game view (0.15, [ADR 0027](adr/0027-gpu-paths.md)): on Windows with Qt Quick on D3D11, hardware frames are no longer read back for the game view; the emulation thread blits them into shared D3D11 textures that the game view draws. Readback runs only while a shared Session needs pixels. Any failure falls back to readback; `UZUME_DISABLE_ZERO_COPY=1` turns it off.
- GPU-direct encoding (0.7.x, [ADR 0019](adr/0019-gpu-direct-nvenc.md)): on NVIDIA, a shared hardware-rendered Session hands the core's OpenGL texture to NVENC through CUDA-GL interop, with no readback or CPU conversion for the encoder. Any problem falls back to the readback path without stopping the Session; `UZUME_DISABLE_GPU_ENCODE=1` turns it off, and the diagnostics host line shows `· GPU-direct` or `· readback (GPU-direct off)`. Verified on an RTX 4080 SUPER (2026-10-11). Since 0.15 the same applies to AMD (`h264_amf`) and Intel (`h264_qsv`) on Windows through an OpenGL to D3D11 bridge ([ADR 0027](adr/0027-gpu-paths.md); verified only locally).
- App UI pass (0.6): Library filter chips with live core state, Settings with server switch/edit/remove (address and port), in-game layout switch, fullscreen (F11; Esc since 0.14 always pauses), Multiview PiP / Row / Grid 2×2 (Row replaced "Side-by-Side" in 0.14), diagnostics overlay split into Emulation and Streaming (F3).
- Hotkeys (0.7.x): Controllers → Hotkeys configures fullscreen (F11), diagnostics (F3), snapshot (F5) and speed-up (Space); Esc is fixed and always pauses and opens the pause card, in a window and in fullscreen (0.14, [ADR 0026](adr/0026-ui-gaps-and-multiview.md)); F11 is the only key that leaves fullscreen. Gamepad hotkeys (0.10.x): hotkey button (default Select) plus a button, per action; tried with virtual joysticks only. Built-in controller profiles are read-only; "Duplicate to edit" copies one.
- Background game (0.7.x): "← Library" pauses the running game and keeps it loaded (a shared Session stays shared); the Library shows "Now running" with Resume and Quit game, and starting another game asks first.
- Saves in the running game: "Manage saves" in the game panel shows slots and history live (snapshot, delete, restore, upload) and resolves conflicts inline; restore and upload apply as a game restart.
- Speed-up / fast-forward (0.7.x, [ADR 0018](adr/0018-player-speed-up.md)): Space or header button, speed 1.5× to 8× (default 2×), for libretro cores that allow it; Emulation settings for speed, speed-up on start and audio; usable while the Session is shared.
- Save sync with the server: sync before launch, auto checkpoint while playing (12 s after the last change, at most every 60 s), final sync on pause, stop and exit; pending uploads are kept per server and user.
- Conflict dialog with "Keep both, decide later" as default; per-game badge Synced / Sync pending / Conflict.
- App identity: the Uzume logo is the window/taskbar icon, the Windows executable icon and the installer icon; the sidebar user block shows the server user name (handshake `user`, stored per server profile) above the device name.
- CLI: `saves list`, `save push`, `save pull`, `save resolve`.
- Share a running game as a Session ("Private" / "Hub users" / "Invite only" with invites, Join/Decline); "Sessions on this Hub" in the library.
- Watch a Session over direct WebRTC (H.264 + Opus); watch-only mode without a running game.
- Multiview: up to 4 surfaces (local game plus up to 3 remote Sessions, or 4 remote Sessions) as Row (2-3 Sessions), Grid 2 x 2 (from 4) or PiP (PiP inside the main tile; docked diagnostics, floating only in fullscreen); exactly one audible surface ("Audio here"); the picker lists all Sessions; diagnostics tab with RTT (negotiated DataChannel `fb-diag`, [protocol](../protocol/datachannel.md)); viewers see "Paused by <name>" on a frozen tile (optional `state` message, 0.14). Encoding runs on a worker thread; under load the oldest pending video frame is dropped.
- Windows: the FFmpeg build enables the NVENC, QSV and AMF H.264 encoders (selected at runtime, software H.264 as fallback). A Windows test checks they are compiled in; opening them needs a GPU and is verified only locally.
- Diagnostics show the connection type (direct / relay), for a relayed path the reason per viewer, and the target bitrate; ICE is logged per connection (0.10.x). During speed-up viewers get evenly spaced base-rate frames. "Collect logs…" (Settings → Diagnostics, CLI `--collect-logs <out.zip>`) writes a redacted zip; the host adapts the encoder bitrate to the worst viewer (AIMD). `UZUME_FORCE_RELAY=1` (CLI `--force-relay`) forces the relay for testing.
- Save comfort: save history with Restore and manual snapshots, slot picker per game, live "save changed on another device" notice; "Upload save file…" in the game's save section (needs `saves_v4`; blocked while the game runs or the slot has pending changes; the local save is backed up first); "Rename slot" and "Delete slot…" for every slot except Main (needs `saves_v5`; delete asks with the latest save and is a hard delete; rename and delete are blocked while the game runs on this app; upload while the game is shared as a Session).
- CLI: `session-share --synthetic`, `session-watch`.
- Credentials in the Credential Manager on Windows; in memory only on Linux and macOS (no OS credential store yet: new pairing and admin approval after every restart, see [guides/player.md](guides/player.md)).
- Redeem an invite code to join a server as a new user (no password).
- Upload ROMs to the server from the app when the server allows user uploads.
- Firmware path for NDS: in native mode the app fetches your firmware files from the server and shows "Firmware required" / "Firmware missing" instead of launching without them.
- Cores come from the server: the app downloads the core for a system on demand (size and SHA-256 checked) into `cache/cores/<core-id>/<version>/<platform>/`; installers ship no cores. CLI: `fetch-core <system-id>`.
- Cores update in the background after the handshake (size and SHA-256 checked, cores in use untouched; 0.10.x). The core probe runs off the GUI thread, the Library grid is virtualized, and a failed save write at stop shows a Library banner. Known slow: Library loading with many (500+) games.
- Emulation page: core options per global/system/game level (game > system > global; locked options are hidden); per game: core choice, speed-up, reset (0.10).
- Nintendo 3DS in the app (0.10): Azahar with two screens (400x240 top, 320x240 bottom touch, composed into a 400x480 frame), OpenGL Core >= 3.3 required (no software fallback, clear error), input profile `3ds` (ZL/ZR, circle pad, C-stick). 3DS saves sync with the server (save source `core_tree`, format `azahar_sdmc`: the game's save data and extdata as one tar; ADR 0022 D3 amendment).
- Game Boy, Game Boy Color and Game Boy Advance in the app (0.13): one screen (160x144, 160x144, 240x160), saves via `SAVE_RAM` (`.sav`) synced like other saves, profiles for mGBA (all three) and Gambatte (GB/GBC; link cable options locked), other cores run as experimental. System manifests carry input maps, game identity and display layout; the Controllers page lists only mapped inputs. Plugin game identity: GBA `gba-gamecode`, GB/GBC `gb-title`. Real cores and games verified only locally.
- Plugin runtime (0.11, packages 1 to 3; [guide](guides/plugin-api.md), [ADR 0023](adr/0023-plugins.md) proposed): sandboxed Lua 5.4 plugins read game memory by virtual address (memory maps from the core, snapshots after the emulated frame) and use native helpers for game-file formats. Developer mode only; install from a folder or link a folder with live reload (all unsigned); Settings → Plugins and an in-game Plugin console. Plugin UI (package 2): declarative blocks and a map view in the in-game tab, HUD, Multiview tile strip, own sidebar screen, game detail section, toasts and plugin hotkeys (Controllers → Hotkeys, Alt+1..9 panel tabs, F4 hides HUD widgets). Server plugins and runs (package 3): the server offers `.fbplugin` files (admin upload with permission ticks, `uzume-server import-plugins`, official signed plugin index by default, `-plugin-index-url none` for offline servers), plugins signed with the Uzume key show as Official, others as Unverified or Local; apps install them from the server with a SHA-256 pin or from a file. The server stores runs (participants, per-player and per-plugin state, event log, plugin boards) and fans them out over WSS; the server web pages Plugins and Runs (admin) show them read-only. The app side is built too: `fb.run` (permission `run.state`) and the Runs screen (invites with plugin consent, run detail, "Start a run", "Play run" with the exact server plugin versions and a per-run save slot; the game picker keeps the library games whose system and server-known game code fit every plugin of the run). Run plugins can declare a rules form (`run_settings`) shown in "Start a run", required plugins are included automatically, and a plugin section (`ui.run`) is shown read-only in the run detail.
- Local ROMs (0.12, [guide](guides/local-roms.md), [ADR 0025](adr/0025-local-roms.md)): Settings → Library folders; the app scans, hashes (cache by path + size + mtime) and registers ROMs, starts them straight from the folder and shows "Local" / "Missing". Games merge by identity (system, game code, version), several files per game, saves stay on one game. Local-only games are visible to their owners (admins see all); optional resumable upload (64 MiB chunks, web 8 MiB, resumes after restarts). Feature `local_roms_v1`; no P2P.
- ROM cache limit (0.10): Settings → `rom_cache_limit_bytes` (default 20 GB, 0 = unlimited), LRU by last use; "Clear ROM cache" with confirmation.
- Operations and safety (0.17, [ADR 0029](adr/0029-operations-and-safety.md)): plugin UI language (Settings → Plugins: Auto | English | Deutsch; Auto uses the 3DS system language for 3DS games); connection check (Settings → Hubs or Diagnostics: server, STUN, TURN relay, NAT type, WebRTC test with a plain-language result); "Report a problem" (description plus redacted logs, settings, connection check and system info to your own server, or "Save as file…"); "Go back" to an earlier app release from the update index.
- Controllers page: SDL3 gamepads, built-in and user profiles, remapping, input test.
- Settings page: Appearance (Dark / Light / System).
- Windows installer (MSI only; the Inno shell was removed in 0.10.x): one WiX MSI for app, server or both (server as Windows service, "Set up a Hub on this PC", standalone mode); CI artifact `uzume-windows-x64-msi` ([ADR 0021](adr/0021-one-windows-installer.md)).
